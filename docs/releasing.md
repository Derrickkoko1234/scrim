# Releasing Scrim

Releases are cut by pushing a version tag. Two workflows react to it:

| Workflow | What it does on a `vX.Y.Z` tag |
| --- | --- |
| [`release.yml`](../.github/workflows/release.yml) (generated by [cargo-dist](https://axodotdev.github.io/cargo-dist/)) | Builds the `scrim` and `git-scrim` binaries for five targets, creates the GitHub Release with archives, checksums, a shell installer and a PowerShell installer, and pushes the Homebrew formula to the tap. |
| [`container.yml`](../.github/workflows/container.yml) | Builds the `scrim-server` image and pushes it to GHCR with `X.Y.Z` and `X.Y` tags (plus the usual `sha-` tag). |

Only `scrim-cli` is distributed as binaries. `scrim-server` is AGPL-3.0-only and
ships exclusively as the GHCR container image (`[package.metadata.dist] dist =
false` in its manifest). `scrim-crypto`, `scrim-policy` and `scrim-cli` are
MIT OR Apache-2.0.

## What cargo-dist builds

Configuration lives in [`dist-workspace.toml`](../dist-workspace.toml) and the
`[profile.dist]` section of the root `Cargo.toml` (release with thin LTO).

- Targets: `aarch64-apple-darwin`, `x86_64-apple-darwin`,
  `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`,
  `x86_64-pc-windows-msvc`.
- Installers: `shell` (`scrim-cli-installer.sh`), `powershell`
  (`scrim-cli-installer.ps1`), `homebrew` (formula `scrim-cli.rb`, tap
  `Derrickkoko1234/homebrew-scrim`). Binaries are installed into `$CARGO_HOME/bin`.
- Archives contain `scrim`, `git-scrim`, `LICENSE-MIT`, `LICENSE-APACHE` and
  `README.md`. The repo-wide `LICENSE-AGPL` is left out on purpose because the
  CLI is not AGPL.
- The linux arm64 build uses GitHub's `ubuntu-22.04-arm` runner, which is only
  available to public repositories (or paid larger-runner plans).

Install commands users get (substitute the real version/tag):

```sh
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/Derrickkoko1234/scrim/releases/latest/download/scrim-cli-installer.sh | sh
brew install Derrickkoko1234/scrim/scrim-cli
cargo install scrim-cli --locked
```

## One-time setup

1. **Tap repository.** Create the empty public repository
   `Derrickkoko1234/homebrew-scrim` (with a default branch, for example by
   adding a README).
2. **`HOMEBREW_TAP_TOKEN` secret** (Settings → Secrets and variables → Actions
   of the main repository). A fine-grained personal access token scoped to the
   `homebrew-scrim` repository only, with *Contents: Read and write*. The
   `publish-homebrew-formula` job uses it to push `Formula/scrim-cli.rb`. The
   built-in `GITHUB_TOKEN` cannot push to another repository.
3. **`CARGO_REGISTRY_TOKEN`** (only needed to publish to crates.io, see below).
   Scope it to `publish-new` and `publish-update`. It is **not** used by any
   workflow today: crates.io publishing is a manual step run from a maintainer
   machine, so keep the token in your own environment rather than in the repo
   unless you later add a publish job.
4. GHCR needs no extra secret: `container.yml` uses `GITHUB_TOKEN` with
   `packages: write`.

## Cutting a release

All crates are versioned in lockstep. cargo-dist announces every dist-able
package that has the tag's version, so `scrim-cli`'s version must match the tag.

1. Start from an up-to-date `main` with green CI.
2. Bump the version everywhere it appears:
   - `version = "X.Y.Z"` in `crates/scrim-policy/Cargo.toml`,
     `crates/scrim-crypto/Cargo.toml`, `crates/scrim-cli/Cargo.toml` and
     `crates/scrim-server/Cargo.toml`;
   - the internal dependency requirements, which currently read
     `version = "0.0.0"`: `scrim-crypto` and `scrim-policy` in
     `crates/scrim-cli/Cargo.toml`, `scrim-policy` in
     `crates/scrim-server/Cargo.toml`, and the `scrim-cli` / `scrim-crypto`
     dev-dependencies in `crates/scrim-server/Cargo.toml`. Set them to
     `X.Y.Z` (or a compatible range such as `"X.Y"`); crates.io rejects a path
     dependency whose version requirement is not satisfied by the published
     crate.
   - `fuzz/Cargo.toml` is standalone and unpublished; leave it.
3. Run `cargo update --workspace` (or `cargo check`) so `Cargo.lock` picks up the
   new versions, then `cargo fmt --all --check`, clippy and `cargo test
   --workspace` as in CI.
4. Check the release plan: `dist plan` (needs `cargo install cargo-dist
   --locked`, pinned to the version in `dist-workspace.toml`) and
   `dist generate --check`.
5. Commit (`Signed-off-by`, see CONTRIBUTING.md), merge to `main`.
6. Tag and push. cargo-dist accepts `X.Y.Z` or `vX.Y.Z`; use **`vX.Y.Z`**
   because `container.yml` only triggers on `v*` tags:

   ```sh
   git tag -s vX.Y.Z -m "Scrim vX.Y.Z"
   git push origin vX.Y.Z
   ```

   Pre-release suffixes (`v1.2.3-rc.1`) mark the GitHub Release as a
   pre-release and skip the Homebrew publish job.
7. Watch the **Release** and **Container** runs. When Release finishes, the
   GitHub Release holds the archives, `sha256.sum`, both installers and
   `scrim-cli.rb`, and the tap has a new commit.
8. Publish to crates.io (below) if the crates are to be installable with
   `cargo install scrim-cli`.

## Publishing to crates.io

`cargo install scrim-cli` needs `scrim-cli` and its path dependencies on
crates.io. Publish in dependency order, waiting for the index to pick up each
crate (usually seconds, run `cargo publish --dry-run -p <crate>` first):

```sh
cargo publish -p scrim-policy
cargo publish -p scrim-crypto
cargo publish -p scrim-cli
```

`scrim-cli` can only be packaged once `scrim-policy` and `scrim-crypto` exist on
crates.io at the version it requires; before that,
`cargo publish --dry-run -p scrim-cli` fails with "no matching package named
`scrim-crypto` found". The same applies to `scrim-server`, which depends on
`scrim-policy` and dev-depends on `scrim-cli` and `scrim-crypto`. Publishing
`scrim-server` is optional (its supported distribution is the container image).
A published version is permanent, so only publish after the tag's Release run
is green.

Package contents are controlled by the `readme`, `keywords`, `categories` and
`exclude` keys in each crate's `[package]` table (`scrim-cli` leaves out its
`tests/` directory). The licence texts are not inside the crate packages; the
SPDX `license` field is what crates.io uses.

## Why `release.yml` does not pin actions by SHA

`ci.yml`, `container.yml` and `dco.yml` pin third-party actions to full commit
SHAs. `release.yml` does not: it is generated by cargo-dist and uses version
tags (`actions/checkout@v6`, `actions/upload-artifact@v7`, ...). The `plan` job
on every pull request runs `dist generate --check`, which fails if the file
differs from what dist emits, so hand-pinning would break CI and would be
overwritten by the next `dist generate`.

Trade-off we accepted: the release workflow is exposed to a moved or
compromised tag of a first-party `actions/*` action, in a job that holds
`contents: write` and the Homebrew token. It also downloads the dist binary
itself from its GitHub release (version-pinned, not hash-pinned) with
`curl | sh`. Mitigations: only `actions/*`
first-party actions are used, the workflow only runs on tags and pull requests
(never `pull_request_target`), and the `HOMEBREW_TAP_TOKEN` is limited to one
repository. If that is not acceptable, set `allow-dirty = ["ci"]` in
`dist-workspace.toml`, pin the actions by hand, and re-apply the pins after each
dist upgrade. Upgrade dist deliberately: `dist init` updates
`cargo-dist-version` and regenerates the workflow, so review that diff.
